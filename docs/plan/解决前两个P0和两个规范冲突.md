已经把 Backup Plan 最关键的“身份”和“设备绑定”边界定稳了。当前 `BACKUPPLAN.md` 也明确记录了剩余顺序：Global Rules → FILE_MANAGED 关系 → Secret → Schedule → History/output → Schema compatibility → Import conflict。

我建议下一轮**同时解决前两个 P0，并顺手消除 `ArchiveUnitId` 与 SelectionFingerprint 的规范冲突**。这三者实际上互相关联。

# 1. 先解决 ArchiveUnitId fingerprint 冲突

我的建议是：

> **`ArchiveUnitId` 不进入 `SelectionFingerprint`。**
>
> `ArchiveUnitId` 是身份键，不是备份选择语义。

当前 Change Detection 把“Archive Unit 的稳定逻辑 identity/path”都列入了 SelectionFingerprint。 我建议修改成：

```text
SelectionFingerprint 包含：
SourceId
ArchiveUnit logical path
Rules
Boundary
LinkPolicy
External Source mapping
各种 semantics version

不包含：
PlanId
ArchiveUnitId
DeviceId
数据库 ID
registration path
```

理由很直接。

假设执行 Clone：

```text
旧：
ArchiveUnitId = A

新：
ArchiveUnitId = B
```

如果其他所有语义完全一样，新 Plan 本来就因为：

```text
PlanId + ArchiveUnitId
```

没有 baseline 而成为 `FirstBackup`，根本不需要再通过 SelectionFingerprint 强制 rebuild。

反过来，如果用户执行明确的 identity migration：

```text
ArchiveUnitId A → B
```

但数据和规则没变，那么这是：

> identity 管理操作

而不是：

> 备份内容变化。

------

## Path 仍然进入 SelectionFingerprint

这一点不要一起删除。

例如：

```text
Source:
projects/A
```

改成：

```text
projects/B
```

即使文件完全一样，逻辑来源发生了变化，而且 manifest、Current 的逻辑结构都可能变化。

所以：

```text
ArchiveUnitId   ❌
ArchiveUnitPath ✅
SourceId        ✅
```

这是比较干净的划分。

对于 FILE_MANAGED，还有一个自然结果：

```text
.backupignore
@id A
```

改成：

```text
@id B
```

虽然 ID 本身不进入 SelectionFingerprint，但 `.backupignore` 是归档内容，所以其文件 bytes 发生变化，`EntrySetFingerprint` 自然变化。当前 `.backupignore` 规范已经规定 own `.backupignore` 被归档。

------

# 2. Global Rules：v1 建议采用“Pinned Snapshot”

这是下一个很重要的决定。

我不建议 `*.backupplan` 写：

```json
{
  "globalRules": {
    "reference": "my-global-rules"
  }
}
```

然后运行时去本机找一个叫 `my-global-rules` 的东西。

因为同一份 Plan：

```text
电脑 A Global Rules = v3

电脑 B Global Rules = v7
```

就会产生不同 ArchivePlan。

这会破坏：

- portability；
- Git 审阅；
- deterministic planning；
- disaster recovery。

因此建议：

> **Backup Plan v1 使用 Global Rules 的 pinned snapshot，而不是运行时 live reference。**

------

# 3. Global Rules Library 仍然可以存在

这不意味着取消“全局规则”。

StowCrate 仍然可以有：

```text
Global Rule Library

Developer Defaults
├─ node_modules/
├─ target/
├─ .venv/
└─ bin/obj/

My Personal Defaults
├─ *.tmp
└─ ...
```

它的作用是：

> 跨 Plan 复用和维护规则模板。

但 Plan 真正执行的，是：

```text
GlobalRuleSnapshot
```

而不是实时读取 library。

流程：

```text
Global Rule Library v4
          ↓
      Apply to Plan
          ↓
Pinned Global Rules Snapshot
          ↓
Backup Plan
```

以后 Library 改成 v5：

```text
Plan
仍然使用 v4 snapshot
```

UI 可以提示：

> 全局规则已有更新。

用户点击：

```text
Apply latest
```

之后：

```text
Plan Snapshot v4 → v5
```

才产生：

```text
RulesChanged
SelectionFingerprint changed
```

------

# 4. 为什么不建议 Global Rules 自动实时影响所有 Plan

备份软件里自动 live reference 风险很高。

假设用户修改一个全局规则：

```text
*.zip
```

结果突然：

```text
50 个 Backup Plan
全部开始排除 zip
```

用户可能根本没有意识到。

Pinned snapshot 更符合：

> 配置变更必须显式、可审阅、可复现。

尤其 File-backed Plan 放 Git 以后：

```text
git checkout abc123
```

应该能恢复当时完整的备份语义。

如果它还依赖电脑里当前 Global Rules，Git 版本就不是完整配置。

------

# 5. Global Rules snapshot 应进入 `*.backupplan`

所以 portable document 最终应保存具体规则：

```text
BackupPlan
├─ GlobalRulesSnapshot
├─ PlanRules
└─ ArchiveUnits
```

不是：

```text
BackupPlan
└─ GlobalRulesReferenceOnly
```

Global Rules Library 的：

```text
GlobalRuleSetId
Revision
Name
```

可以作为可选 **provenance metadata**。

例如概念上：

```json
{
  "globalRules": {
    "provenance": {
      "name": "Developer Defaults",
      "revision": 4
    },
    "rules": [
      "node_modules/",
      "target/"
    ]
  }
}
```

但真正 authoritative 的是：

```text
rules
```

不是 provenance。

因此即使另一台电脑根本不存在：

```text
Developer Defaults
```

Plan 也照样能执行。

------

# 6. Global Rules provenance 不进入备份 fingerprint

例如：

```text
name:
Developer Defaults
→
My Developer Defaults
```

而规则内容没变：

```text
SelectionFingerprint 不变
```

真正进入 fingerprint 的：

```text
规则 action
pattern
规则顺序
rule semantics version
```

而不是：

```text
Library ID
Library display name
更新时间
```

------

# 7. Managed 和 File-backed 在这里保持完全一致

### MANAGED

SQLite 保存：

```text
Pinned Global Rules Snapshot
```

可以额外保存：

```text
来自哪个 GlobalRuleSet
来自哪个 revision
```

用于 UI 提示更新。

### FILE_BACKED

`*.backupplan` 自己保存：

```text
Pinned Global Rules Snapshot
```

不允许执行时去读本机 Global Rule Library。

因此：

```text
ResolvedPlanSnapshot
```

完全一样。

Planning Kernel 仍然不知道：

```text
Managed / File-backed
```

------

# 8. Rule Engine 最终仍然保持现在的三层模型

一点都不用改：

```text
Pinned Global Rules Snapshot
          ↓
       Plan Rules
          ↓
      Local Rules
```

仍然：

```text
Global → Plan → Local
Last Match Wins
```

当前 `.backupignore` 已经正式规定了这一语义。

------

# 9. 接下来是 FILE_MANAGED declaration

这里建议明确区分两个概念：

```text
Discovery
```

和：

```text
Declaration
```

不要混成一个。

------

# 10. FILE_MANAGED Archive Unit 的存在由磁盘决定

我们已经规定：

```text
目录存在 .backupignore
=
FILE_MANAGED Archive Unit
```

因此：

> **Backup Plan declaration 不是 FILE_MANAGED Archive Unit 存在的必要条件。**

例如：

```text
Source
├─ A
│  └─ .backupignore
│
└─ B
   └─ .backupignore
```

即使 `.backupplan` 完全没有列：

```text
A
B
```

Scanner/Discovery 仍然必须发现：

```text
A
B
```

不能变成：

> Plan 没声明，所以忽略。

这符合现有 `.backupignore` 规范：Archive Unit Discovery 独立于规则执行。

------

# 11. 那 Backup Plan declaration 是干什么的？

它的作用应该定义成：

> **给一个已存在/应存在的 Archive Unit 附加 portable configuration。**

例如以后：

```text
ArchiveSpec Override
History Override
Display Name
External Source Mapping
其他 per-unit portable settings
```

因此：

```text
.backupignore
```

负责：

```text
Unit existence
Local RuleMode
Local case
Local Rules
optional @id
```

而：

```text
Backup Plan declaration
```

负责：

```text
portable identity association
logical expected path
non-rule per-unit configuration
```

两者职责明确分开。

------

# 12. FILE_MANAGED declaration 绝不能保存 Local Rules

这是必须写死的。

例如不允许：

```json
{
  "ruleSource": "file",
  "mode": "exclude",
  "rules": [
    "node_modules/"
  ]
}
```

因为：

```text
ruleSource = FILE_MANAGED
```

之后：

```text
RuleMode
Rules
Case
```

全部由：

```text
.backupignore
```

决定。

否则又回到双真相源。

当前规范已经明确 FILE_MANAGED 时 SQLite 不能另存 RuleMode/Rules。

同样道理适用于：

```text
*.backupplan
```

------

# 13. 建议 declaration 概念结构

暂时不要定 JSON 字段，只定领域模型。

```text
ArchiveUnitDeclaration
├─ ArchiveUnitId
├─ SourceId
├─ Path
├─ RuleSource
└─ PortableOverrides?
```

其中：

```text
RuleSource
├─ UI_MANAGED
└─ FILE_MANAGED
```

如果：

```text
UI_MANAGED
```

则 declaration 自己携带：

```text
LocalRuleSet
```

如果：

```text
FILE_MANAGED
```

则：

```text
LocalRuleSet = forbidden
```

------

# 14. FILE_MANAGED discovery 的四种情况

这个最好正式定义成状态表。

## A. `.backupignore @id` + Plan declaration

例如：

```text
Plan:
ArchiveUnitId = A
Path = Project
```

磁盘：

```text
Project/.backupignore
@id A
```

结果：

```text
MATCH
```

正常。

------

## B. 没有 `@id` + Plan declaration

Plan：

```text
ArchiveUnitId = A
Path = Project
```

磁盘：

```text
Project/.backupignore
```

无 ID。

那么：

> Plan declaration 提供 portable identity。

本轮运行：

```text
Project
→ ArchiveUnitId A
```

完全合法。

不要求修改 `.backupignore`。

------

# 15. 有 `@id`，但没有 Plan declaration

例如磁盘：

```text
Project/.backupignore
@id A
```

Plan 没写 Project。

也应该正常：

```text
Discovered FILE_MANAGED ArchiveUnit
ArchiveUnitId = A
```

使用：

```text
Plan-level defaults
```

它仍然是真正的 Archive Unit。

这样 `.backupignore` 才能独立工作。

------

# 16. 无 `@id`，也无 declaration

最普通情况：

```text
Project/.backupignore
```

Plan 没声明。

结果仍然：

```text
Discovered FILE_MANAGED ArchiveUnit
```

本机 registration 给它：

```text
ArchiveUnitId = generated UUID
```

但：

> 这个 ID 只有当前设备稳定。

目录 rename 后：

```text
旧 unit deleted
新 unit discovered
```

这是刚刚已经确定的规则。

------

# 17. Identity 匹配顺序

建议正式定义：

```text
1. @id
2. explicit Plan declaration
3. local registration by SourceId + RelativePath
4. generate new local ArchiveUnitId
```

但这里有一个重要限制：

> 不能让后面的步骤覆盖前面的显式 identity。

例如：

```text
.backupignore @id = A

Plan declaration:
ArchiveUnitId = B
Path = same
```

必须：

```text
Fatal IdentityConflict
```

不能说：

> Plan 优先。

也不能说：

> file 优先。

------

# 18. 如果相同 @id 出现在不同路径

例如：

```text
A/.backupignore
@id X

B/.backupignore
@id X
```

直接：

```text
Fatal DuplicateArchiveUnitIdentity
```

这一点现有规范已经规定同一 Plan 重复 ArchiveUnitId 是 Fatal。

------

# 19. declaration Path 与实际 `@id` 路径不一致

这是一个非常重要的新情况。

Plan：

```text
ArchiveUnitId = X
Path = OldName
```

磁盘发现：

```text
NewName/.backupignore
@id X
```

我建议：

> **不要自动跟随到 NewName 执行。**

而应该返回：

```text
ArchiveUnitRelocated
PlanNotReady
```

原因是：

```text
*.backupplan
```

是 declarative desired configuration。

Plan 明明声明：

```text
OldName
```

StowCrate 不应该偷偷把它解释成：

```text
NewName
```

UI 可以提示：

> 发现具有相同 ArchiveUnitId 的归档箱位于 `NewName`，是否更新方案路径？

用户确认：

```text
OldName → NewName
```

之后才执行。

这符合我们一直坚持的：

> 不自动猜配置。

------

# 20. Managed Plan 也是一样

即使是 Managed：

```text
Path = OldName
```

发现：

```text
@id X 位于 NewName
```

也不要静默修改 SQLite。

可以：

```text
Detected relocation
```

然后用户确认。

FILE_BACKED 更不能自动写回 `.backupplan`。

------

# 21. declaration 要求存在，但实际 `.backupignore` 不存在

Plan：

```text
RuleSource = FILE_MANAGED
Path = Project
```

但：

```text
Project/.backupignore
```

不存在。

这应该：

```text
PlanNotReady / MissingFileManagedRuleSource
```

Fatal validation。

绝不能：

```text
“那就当 UI_MANAGED”
```

或者：

```text
“没有 local rules，继续”
```

因为 declaration 明确说：

```text
FILE_MANAGED
```

------

# 22. UI_MANAGED + `.backupignore`

现有规则继续保持：

```text
Plan declaration:
UI_MANAGED Project
```

磁盘：

```text
Project/.backupignore exists
```

结果：

```text
RuleSourceConflict
Fatal
```

不得偷偷优先任何一方。

------

# 23. 未声明 FILE_MANAGED unit 是否允许 per-unit override？

我建议：

> **不允许 portable per-unit override。**

因为 Plan 不知道怎么稳定引用它。

例如：

```text
Project/.backupignore
```

没有：

```text
@id
```

也没 declaration。

它可以：

```text
正常备份
使用 plan defaults
```

但如果用户要设置：

```text
这个 Crate 用 ZIP
这个 Crate 保留 History 30 天
```

就应该：

> 将它添加为 Plan declaration。

这样形成稳定：

```text
ArchiveUnitId
```

这比偷偷通过 path 建 override 要好。

------

# 24. 对带 `@id` 但未 declaration 的 Unit 呢？

理论上 Plan 可以通过 ID 引用。

但 v1 我仍建议保持简单：

> per-unit portable override 要求存在 declaration。

因为 declaration 不只是 identity，还表达：

```text
这是 Plan 明确配置的一部分
```

否则 JSON 里会出现：

```text
override X
```

但 `archiveUnits` 根本没有 X，很难审阅。

------

# 25. Discovery Unit 与 Declared Unit

因此可以正式形成：

```text
ArchiveUnitOrigin
├─ Declared
└─ Discovered
```

但是：

> Origin 不属于 Core backup semantics。

最终进入 Planning Kernel 后还是统一：

```text
ArchiveUnit
```

Application resolution 阶段负责：

```text
Declared configuration
+
Physical discovery
+
.backupignore metadata
+
local registration
        ↓
Resolved ArchiveUnit
```

这与现在 `ResolvedPlanSnapshot` 的思路完全一致。

------

# 26. FILE_MANAGED Unit 的 Local Rule resolution

最终每个 Unit：

```text
Pinned Global Rules
      ↓
Plan Rules
      ↓
.backupignore Local Rules
```

如果：

```text
FILE_MANAGED
```

Application 必须读取：

```text
.backupignore
```

得到：

```text
ArchiveUnitId?
RuleMode
CasePolicy
Rules
```

然后产生：

```text
ResolvedArchiveUnit
```

Planning Kernel 不再需要读取物理文件。

------

# 27. `.backupignore` 修改时的 stale plan 检查

这里也值得明确。

File-backed `.backupplan` 有：

```text
PlanSemanticFingerprint
```

但 `.backupignore` 本身不是 Backup Plan Document。

所以运行开始时还应该捕获：

```text
ResolvedSelectionFingerprint
```

或者等价的：

```text
RuleSourceFingerprint
```

Publish 前重新检查 FILE_MANAGED rule source 是否改变。

否则：

```text
Scan 时 rules = A

压缩过程中
.backupignore 改成 B

最后仍然 publish A
```

就有语义漂移。

当前 Change Detection 已经要求发布前重新验证 PlanSemanticFingerprint；这里建议扩展成：

```text
ExecutionSemanticSnapshot
=
PlanSemanticFingerprint
+
Resolved external rule source fingerprints
```

如果 `.backupignore` 改变：

```text
ConfigurationChangedDuringRun
```

不发布、不推进 baseline。

这个名字是否继续统一为：

```text
PlanChangedDuringRun
```

都可以，但概念上需要覆盖外部 rule source。

# 28. Global Rules + FILE_MANAGED 最终模型

到这里整个规则系统就很清楚：

```text
Global Rule Library
        │
        │ explicit apply/update
        ▼
Pinned Global Rules Snapshot
        │
        ▼
*.backupplan / Managed Plan
        │
      Plan Rules
        │
        ▼
ResolvedPlanSnapshot
        │
        ├── UI_MANAGED
        │      Local Rules from Plan
        │
        └── FILE_MANAGED
               Local Rules from .backupignore
                    │
                    ▼
             EffectiveRuleSet
```

三层规则逻辑完全没有改变。

# 29. 这次建议一起写进规范的 fingerprint 修正

建议正式改成：

### SelectionFingerprint 包含

```text
SourceId
ArchiveUnitPath
Global Rules Snapshot
Plan Rules
Local Rules
RuleMode
Case
Resolved case
Boundary Tree
LinkPolicy
External Source Mapping
semantics versions
```

### 不包含

```text
PlanId
ArchiveUnitId
ExternalSourceId 本身*
DeviceId
authority
registration path
Global Rule Library ID
Global Rule Library revision/name
```

这里 `ExternalSourceId` 稍微特殊：

如果只是 identity，就不应该因为 UUID 改变导致 bytes 重建。

真正进入 fingerprint 的应该是：

```text
External source logical mapping
archive destination
相关 selection semantics
```

但 baseline/manifest 仍记录 ID。

这和 ArchiveUnitId 是同样原则：

> **Identity ≠ content semantics。**

# 30. 我建议下一轮一次完成这三项

1. **解决 ArchiveUnitId / SelectionFingerprint 正式规范冲突**
   - identity 本身不进入 SelectionFingerprint；
   - SourceId、ArchiveUnit logical path 和真正选择语义继续进入；
   - 同步 `CHANGE-DETECTION.md`、`BACKUPPLAN.md`、`BACKUPIGNORE.md`。
2. **正式确定 Global Rules v1 为 pinned snapshot**
   - Global Rule Library 是 authoring/reuse facility；
   - Plan execution 只使用 concrete snapshot；
   - v1 不支持 live external Global Rules reference；
   - optional provenance 不 authoritative、不进入 fingerprint。
3. **正式确定 FILE_MANAGED discovery/declaration resolution**
   - `.backupignore` existence 声明 Unit；
   - declaration 非存在条件；
   - declaration 负责 identity association 和 portable per-unit settings；
   - FILE_MANAGED declaration 禁止携带 Local RuleMode/Case/Rules；
   - 明确四种 discovery/declaration 情况；
   - missing file、identity conflict、relocation、UI/FILE conflict 都安全失败。

然后：

> **仍然不要写 JSON Schema，也不要实现代码。**

这三项完成以后，`*.backupplan` 的核心结构实际上就已经成型大半了；下一项再进入 Secret Reference / Encryption，会更顺。
