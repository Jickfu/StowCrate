# Milestone 4 Completion Review

## 结论

**PASS — M4 COMPLETE。**

M4 已形成从 `ExecutionReadyArchive` / `ArchiveBuildRequest` 到 `VerifiedArchiveArtifact` 的完整工具无关边界。PASS 的含义不是每种 portable Protection 都已有实现，而是所有已声明 Supported 的组合都能完成真实写入和验证，Unsupported 组合会在 `.partial` 写入前准确失败。Physical Current/History Publisher、PublishIntent execution 与 baseline commit 仍未实现。

三平台 authority evidence 为 GitHub Actions CI run [33537240941](https://github.com/Jickfu/StowCrate/actions/runs/33537240941)，对应代码 `e2141e18310a4f94272ced94c62e36226449d87b`：Windows x64、Linux x64、macOS x64 的 build、bundled 7-Zip 26.02 integrity probe 与全部测试均通过。此前 Windows fixture 曾真实发现7zz console listing丢失Unicode；修复后同时固定`-sccUTF-8`、UTF-8 process decoding及ZIP `-mcu=on`，不以降低fixture expectation规避问题。

## Backend catalog 与执行边界

Archiving 内部 `ArchiveBackendCatalog` 将 semantic identity、capability resolver、writer与verifier绑定为registration。按`ArchiveCapabilityRequirements + archiveSemanticsVersion`解析时，0个匹配返回Unsupported，1个匹配返回exact backend，多匹配返回明确ambiguous configuration failure；catalog dispatcher再按已解析capability semantics选择writer/verifier。Application仍只依赖M4 ports，不感知7zz、ZstdSharp、executable path或switch。

失败、取消、format corruption、entry/manifest mismatch均不能构造Verified lifecycle；只有format test、exact entry set、durable manifest cross-check、最终SHA-256/length全部成功才调用`ArchiveVersion.Prepare(...).Verify(...)`。本阶段没有创建`CurrentVersion`、`HistoryVersionPlacement`、`PublishIntent`或`CommittedBaseline`。

| Backend | RID | Compression | Metadata/link声明 | Protection |
|---|---|---|---|---|
| SevenZip 26.02 / 7z | win-x64, linux-x64, osx-x64 | Store/Fast/Standard/Extreme | UTC mtime；不声明flags或links | None |
| SevenZip 26.02 / ZIP | win-x64, linux-x64, osx-x64 | Store/Fast/Standard/Extreme | UTC mtime；UTF-8 names；不声明flags或links | None |

SevenZip/ZIP symbolic links和ReadOnly/Hidden/Executable继续Unsupported；TarZstd Hidden以及Junction/MountPoint/Other link继续Unsupported。resolver按required metadata flags ⊆ preserved flags判定，不能silent loss。

## Durable contracts 与 corruption taxonomy

Manifest v1 与 Privacy Recovery Envelope v1均为closed-world、case-sensitive contract。Envelope的`archiveFormat`仅显式接受`SevenZip|Zip|TarZstd`，numeric、unknown、case variant、duplicate、missing与future semantics fixtures全部fail closed。Recovery material为crypto RNG生成的32 bytes、无paddingbase64url ASCII；归档内bytes必须与本轮generated bytes一致，且不进入普通manifest或fingerprint。

TarZstd verifier将truncated/corrupt Zstd frame、损坏Tar数据、unsupported Tar entry稳定映射为format-test failure；只捕获明确的`ZstdException`、`InvalidDataException`、`EndOfStreamException`与archive-stream `IOException`，不使用无边界catch隐藏程序错误。

## Reproducibility 与标准互操作

M4的deterministic保证定义为**semantic determinism**：相同Candidate、ArchiveSpec与CapabilitySemantics必须得到相同entry/manifest语义。managed TarZstd的相同materialized input已额外证明byte-identical；其semantics固定PAX、entry ordinal、uid/gid=0、空user/group、mtime/mode映射、ZstdSharp.Port 0.8.8、upstream zstd 1.5.7、levels 1/6/19与content checksum=true。

7z/ZIP不宣称`byte-reproducible v1`；M4只要求semantic determinism，避免把backend container metadata或未来library实现细节误写为byte contract。7z固定7-Zip 26.02、7z container、LZMA2、solid与level mapping；ZIP固定Deflate/Copy、UTF-8 names与level mapping。ZIP由.NET `ZipArchive`独立读取payload/manifest，7z由pinned 7zz正常extract，TarZstd由独立decompression + `TarReader`路径读取，均为标准archive而非StowCrate私有wrapper。

## Privacy、Secure 与安全泄漏结论

Privacy Recovery Envelope v1 contract已冻结，但当前backend support为none。SevenZip/ZIP mixed-encryption尚无三平台完整证据；TarZstd Privacy保持Unsupported且不使用skippable frame、sidecar、comment或私有加密wrapper。Privacy明确不提供机密性保证。

Secure是合法portable configuration，但当前backend capability均Unsupported。7zz `-p{password}`会暴露argv；redirected-stdin Unicode material未证明完整write/test/list/read窗口可靠，因此没有argv、environment、response-file或不安全fallback。Unsupported Secure/Privacy在backend选择与readiness阶段停止，不启动带password进程。

Manifest/archive bytes不包含Source/External/Current/History physical path；diagnostics不包含Secret material、provider或opaque locator。Secret lease仍只覆盖最短writer/verifier窗口，并在成功、失败、取消后dispose/zeroize。
